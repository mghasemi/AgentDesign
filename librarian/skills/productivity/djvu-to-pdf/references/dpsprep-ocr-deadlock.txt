EVIDENCE: dpsprep 2.8.3 OCR path deadlocks (do not use --socr)
============================================================

Captured: 2026-09-17, host pop/24.04 (Linux 7.1.5), python 3.12, dpsprep 2.8.3,
djvulibre-python 0.9.3, ocrmypdf 17.12.1 (venv) / 15.2.0 (apt).

Reproduction (hangs indefinitely; no error, no timeout):

    rm -rf /var/tmp/dpsprep/*
    PYTHONFAULTHANDLER=1 dpsprep -p 1 -q 85 --socr eng -f fixture_notext.djvu out.pdf

Symptom: stdout reaches "Failed to encode page N. Trying again without setting
quality" for all pages, page_bg_{1,2,3}.pdf appear in /var/tmp/dpsprep/<hash>/,
then the process sleeps forever. No worker children remain alive (no tesseract,
no gs, no ocrmypdf subprocess) - it is a pure-python wait, not a busy subprocess.
Reproduced with -p 1 and with a cleared working directory.

Diagnosis: SIGABRT with PYTHONFAULTHANDLER=1 dumps the stack below; the main
thread polls a multiprocessing connection for results that never arrive, because
the workers died. There is no timeout in dpsprep, so a dead worker means a
permanent hang rather than a failure.

Note: rc=134 in a shell means 128+6 = SIGABRT. If a background wrapper reports
rc=134 for a dpsprep run, check whether the dump was self-inflicted (this file)
before treating it as a crash.

Control checks that isolate the fault to dpsprep, not OCRmyPDF:

  - /usr/bin/ocrmypdf (15.2.0) OCRs a raster PDF correctly in ~1s.
  - venv ocrmypdf (17.12.1) does the same, rc=0.
  - djvu2pdf -m ocr (ddjvu raster -> ocrmypdf CLI) works: 3 pages ~0.4s.
