\begin{executive}

This document records the complete design of the two Hermes agent profiles that power my
mathematical research workflow --- \textbf{\mono{math}} and \textbf{\mono{librarian}} --- and
specifies an abstraction layer under which either profile can be re-pointed at any future math
project without modification. Sanitized, ready-to-use copies of both profiles ship with this
document as the \mono{math/} and \mono{librarian/} folders (Section~\ref{sec:folders}); the
companion artifacts listed in the closing Sources and Verification note let every claim here be
re-derived from a live installation.

The architecture resolves into five layers: a shared \emph{Hermes core}, an isolated
\emph{profile system}, a \emph{skill catalog} (capability-gated per profile), an \emph{MCP bridge}
(native servers plus a generic CLI-adapter pattern), and an \emph{external service plane}. The math
profile is a full-stack researcher with a sandboxed toolchain environment; the librarian profile is
a capability-degraded derivative that shares every registration but disables the computational
surface and adds ingestion skills of its own.

Two structural findings drive the abstraction design: (i)~the librarian profile's MCP servers
import scripts from the math profile's directory tree, so it cannot exist without the math
profile; and (ii)~both profiles carry a stale reference to a development worktree that no longer
exists (a merge left the registered path dangling). Section~\ref{sec:abstraction}
proposes a capability/manifest model --- persona templates, path interpolation, a shared adapter,
a service registry, and per-project binding files --- that removes every identified coupling in
five concrete steps.

\end{executive}

\section{Objectives and Scope}\label{objectives}

The \mono{AgentDesign} project has three objectives:

\begin{enumerate}
    \item \textbf{Document the as-is architecture.} Record, with file-level evidence, how the
    math and librarian profiles are composed: directory layout, configuration sections, skill
    catalogs, MCP server registrations, external services, scheduled jobs, and state stores.
    This is Sections~\ref{sec:layers}--\ref{sec:workflow}.
    \item \textbf{Identify the coupling points.} Enumerate every place where a profile depends
    on the specific current project layout --- absolute paths, cross-profile imports, hardcoded
    endpoints, and stale references --- so that the design of record distinguishes what is
    load-bearing from what is incidental (Section~\ref{sec:defects}).
    \item \textbf{Specify an abstraction layer.} Define how profiles become reusable personas:
    independent of any particular math project, instantiable for a new project with zero or one
    line of configuration, and testable against a capability contract
    (Section~\ref{sec:abstraction}).
\end{enumerate}

The scope is the two active research profiles. The remaining four registered profiles
(\mono{default}, \mono{coder}, \mono{advisor}, \mono{trader}) are out of scope; their existence
is noted only in Section~\ref{sec:profiles}. This project does not modify any live profile
configuration --- it is a documentation and design artifact.

\subsection*{Layer 0 --- Hermes Core}
The core lives at \mono{\textasciitilde/.hermes/hermes-agent/}: agent runtime, CLI (profile
switching, tool registry), platform gateway (Telegram/WhatsApp/webhook adapters), built-in tools
(terminal, browser, vision, file I/O, web search, kanban, memory) and the MCP discovery layer
(\mono{tools/mcp\_tool\_*.py}). Shared binaries (\mono{tirith} security scanner, \mono{uv}, Python
3.14, Node 26, ripgrep, Chromium) live in \mono{\textasciitilde/.hermes/tools/}; all MCP stdio
servers run from a single shared virtualenv at \mono{\textasciitilde/.hermes/mcp-servers/.venv/}.

\subsection*{Layer 1 --- Profile System}
Each profile is an isolated directory with its own configuration, credentials, state and sandbox.
The two profiles under study:

\begin{itemize}
    \item \textbf{\mono{math}} --- full-stack mathematical researcher. It owns a sandboxed home
    environment carrying the local toolchain (Section~\ref{sec:profiles}), an active messaging
    gateway, and the scheduled literature jobs.
    \item \textbf{\mono{librarian}} --- literature manager (``manage and maintain books and
    articles''). It keeps an empty sandbox home, registers no scheduled jobs and no messaging
    platform, and reuses the same kanban assignment as math --- itself a coupling noted in
    Section~\ref{sec:defects}.
\end{itemize}

Both profiles run the same local model through LM Studio, with an \mono{on\_session\_start} hook
that guarantees the model server is up before each session. Long-term memory in both profiles is
backed by Honcho (\mono{memory.provider: honcho}).

\subsection*{Layer 2 --- Skill Catalog}
Skills are Markdown-defined capability units (\mono{SKILL.md} with YAML frontmatter), organized
in category directories, optionally carrying scripts and credential files. Each profile holds the
same catalog --- nine populated categories plus a handful of top-level skills, and the same empty
category shells --- and differs only in which entries are activated. The per-profile inventory
extracted from a live installation is kept in \mono{references/skill\_inventory.md};
Section~\ref{sec:skills} summarizes the design-relevant parts.

\subsection*{Layer 3 --- MCP Bridge}
Skills reach services either directly (terminal/shell) or through Model Context Protocol servers
registered in each profile's config; every registered tool is exposed to the model under a name
built from the server and the tool, joined by double underscores --- for example, the vikunja
task-creation tool. Section~\ref{sec:mcp} documents the two server families and the cross-profile
dependency this layer creates.

\subsection*{Layer 4 --- Service Plane}
A fixed set of self-hosted services on the local network, plus SaaS APIs and a local inference
server. Table~\ref{tab:services} lists them with their role in the workflow.

\textbf{The librarian is a capability-degraded derivative of math}, not an independent design: it
inherits every skill directory and MCP registration, then suppresses the computational surface via
the \mono{skills.disabled} list. It also carries two skills that exist only in its own tree ---
\mono{calibre-library-ingestion} and \mono{djvu-to-pdf} (productivity category) --- which is where
its genuine specialization lives.

The math profile carries a sandboxed home directory that stands in for a machine-local toolchain.
It holds a Lean 4 installation managed by elan, a Rust toolchain together with its registry and
download caches, a dedicated browser profile for NotebookLM grounded synthesis, runtime state
directories for SageMath and Maxima, and the font and format caches of TeX Live. Two properties
matter for the abstraction design. First, most of the space is disposable package cache rather than
toolchain state: the load-bearing parts are the Lean and Rust installations, everything else can be
re-provisioned. Second, the sandbox is not self-contained --- the SageMath and TeX Live binaries
resolve to host-level installations rather than to anything inside the profile home --- so a
profile's computational capability depends on the host even when it looks self-contained.

\section{Folder Structure}\label{sec:folders}

Three directory levels carry the design: the shared Hermes root, the two profile trees, and the
per-project binding file. The listings below show the structure with the design-relevant entries;
the profile skeleton in Listing~\ref{lst:profiletree} marks which entries exist in which profile.

\subsection*{Shared root}

The \mono{\textasciitilde/.hermes/} root holds everything that is not profile-scoped. Two entries
are load-bearing for the coupling analysis: \mono{mcp-servers/} holds the single Python environment
that every MCP server of every profile runs in, and \mono{skills/} is the shared pool that both
profiles fall back to for both skills and plugins.

\begin{lstlisting}[label=lst:hermesroot]
~/.hermes/                          # shared Hermes root
  config.yaml                       # global defaults; profiles override
  profiles/                         # one directory per profile (math, librarian, advisor, ...)
  skills/                           # shared skill pool: 17 categories
  plugins/                          # shared plugin installs: vikunja, wiki-browser, hermes-achievements
  desktop-plugins/                  # desktop plugin surfaces: vikunja, wiki-browser
  plugin-data/                      # per-plugin persistent state: hermes-achievements
  mcp-servers/.venv/                # ONE Python env for all 13 MCP servers
  memories/  sessions/  state.db    # memory files, session store, global state
  kanban/  kanban.db                # kanban board + dispatcher state
  cron/  hooks/  agent-hooks/       # scheduling and lifecycle hooks
  bin/  node/  webui/  tools/       # runtime binaries, desktop build, CLI tools
\end{lstlisting}

\subsection*{Profile tree: the two profiles side by side}

The math profile is a structural superset: it carries the runtime residue of an active profile,
while the librarian keeps only what its role needs. Two differences are design-relevant ---
\mono{scripts/}, the MCP adapter directory, exists only on the math side, and \mono{home/} is
populated only there. Those two facts are the structural root of the path coupling in
Section~\ref{sec:mcp}.

\subsection*{Distributable profile packs}\label{sec:packs}

The \mono{math/} and \mono{librarian/} folders inside this project are sanitized, ready-to-use
copies of the two profiles: the same directory structure, the same configuration and skill trees,
with every credential, endpoint, hostname and local path replaced by a placeholder, and with the
per-installation bookkeeping (the loader, curator and telemetry files listed above) left out. A builder script
in \mono{references/} copies the configuration, skill, plugin, script and memory trees from a live
installation, scrubs secrets and identity, and writes a per-pack \mono{README.md}. Copying a pack into \mono{\textasciitilde/.hermes/profiles/} and
filling in the placeholders reproduces the profile; the packs are described in
Section~\ref{sec:packs}.

\end{lstlisting}

The \mono{stack/} folder turns the service plane of Section~\ref{sec:services} into an executable
artifact: one compose project that brings up every container the two profiles talk to, with
credentials interpolated from an untracked \mono{.env}. Its \mono{README.md} maps each container to
the MCP server or skill that consumes it and records what the live deployment gets wrong.

Reproducing the build requires one environment step beyond the template: the CPI style loads the
Garamond T1 fonts, which are not part of a stock TeX Live installation. They are installed
per-user (no root) under \mono{\textasciitilde/texmf/} --- \mono{ggm*.tfm} in \mono{fonts/tfm/ggm/},
\mono{ggm*.vf} in \mono{fonts/vf/ggm/}, \mono{ggm*.pfb} in \mono{fonts/type1/ggm/}, \mono{ggm.map}
in \mono{dvips/ggm/}, then \mono{mktexlsr \textasciitilde/texmf}. Without it the build fails at the
first page with a missing-font error rather than a document error.

\section{Skill System: Design for General Math Projects}\label{sec:skills}

Skills are the unit of reusability. Each \mono{SKILL.md} carries a trigger description in its
frontmatter, an imperative body, optional scripts, and --- where needed --- a credential file
(\mono{.emv}) co-located with the skill that consumes it. The catalog is shared
between the two profiles: the same populated categories, the same empty category shells, and the
same top-level skills, with a single exception --- \mono{irene-rewrite-dev} is an active top-level
skill in math and a curator tombstone in the librarian. Only activation differs. Table~\ref{tab:skillcats}
summarizes the catalog by design role; the per-entry inventory extracted from a live installation is
in \mono{references/skill\_inventory.md}.

Three observations are design-relevant:

\begin{enumerate}
    \item \textbf{The math research surface is exactly the set of skills a generic math project
    needs}: decompose $\to$ literature $\to$ compute $\to$ verify $\to$ write, implemented by
    \mono{math-research-workflow}, whose frontmatter names the sibling skills it relies on. This
    set, not the full catalog, defines the reusable ``mathematician'' capability contract
    (Section~\ref{sec:abstraction}).
    \item \textbf{The librarian's disabled list is a negative specification of that same
    contract}: every computational skill (\mono{sagemath-mcp}, \mono{sympy-mcp},
    \mono{lean4}, \mono{lean4-goedel-agent}, \mono{scientific-coding}), the DSDP skills, and the
    Irene/dev skills are turned off. Capability gating by negation works today but is brittle in a
    subtler way than it looks: entries resolve by \emph{leaf name} against the profile's skill tree,
    which includes the curator tombstone directory \mono{skills/.archive/}. Every disabled name
    therefore resolves to a real \mono{SKILL.md}; none dangles. But a sizeable minority of them
    resolve \emph{only} under \mono{.archive/} --- they are residue from skills the curator has
    already retired (\mono{docx}, \mono{opencode}, \mono{test-driven-development}, and for the
    librarian also \mono{irene-rewrite-dev}, which is an \emph{active} top-level skill in math while
    pointing at a librarian tombstone). Because resolution is name-based, any of these stale entries
    would silently disable a same-named skill if it were ever reinstalled. One inversion deserves note: \mono{reddit-reading} is
    disabled for math but enabled for librarian --- the only skill whose gate runs opposite to every
    other difference between the two profiles.
    \item \textbf{One reference is stale}: \mono{math-research-workflow} names
    \mono{simplerag-memory} in its frontmatter and body, several times as shell invocations of a
    client script that does not exist; no such skill exists in either profile tree or in the bundled
    pool.
\end{enumerate}

The \textbf{generic CLI-adapter pattern} is the load-bearing design of this layer. A single script ---
the generic adapter kept in the profile's \mono{scripts/} directory --- wraps any argparse-based Python CLI tool as a
stdio MCP server: it introspects the target's parser at startup, exposes each subcommand as an MCP
tool with JSON-schema arguments, and reconstructs command lines from tool calls. Most of the
registered servers use it; adding a new service-backed skill therefore requires only a thin CLI
script plus a config entry (endpoint and token via environment), with no protocol code.

Two cross-profile facts follow directly from the table:

\begin{itemize}
    \item Every path in every MCP registration --- including all of the librarian's --- points into
    the \textbf{math profile's directory tree}: every adapter tool script, every native server
    script, and the adapter itself. The librarian has no \mono{scripts/} directory of its own.
    Deleting or moving the math profile would silently break every tool-bridged capability of the
    librarian.
    \item Both profiles register \mono{hermes-irene} against a script inside a development worktree
    that was merged into the main \mono{Irene} package and then removed; the file was never
    committed, so the registration dangles. It is dormant in math and left enabled in the librarian,
    where it fails at startup. The correct target is the merged package, where no such script has yet
    been created.
\end{itemize}

\section{Toward an Abstraction Layer}\label{sec:abstraction}

The goal is a design in which \emph{profiles are personas and projects are bindings}. A profile
declares \textbf{what it can do} (capabilities) and \emph{how it behaves} (persona); a project
declares \textbf{where things live} (paths, endpoints, ledgers). Nothing in today's configuration
should need editing to attach the existing math or librarian profile to a new math project.

\subsection*{A. Capability-gated skill activation (replaces negative lists)}

Each \mono{SKILL.md} gains one frontmatter field:

\begin{lstlisting}[language=Python]
requires: [computation, formal-proof]   # empty list = always available
\end{lstlisting}

and each profile declares a positive capability set instead of a disabled list:

\begin{center}\small
\renewcommand{\arraystretch}{1.15}
\begin{tabularx}{\textwidth}{@{}l X@{}}
\toprule
Persona & Capabilities\\
\midrule
\mono{mathematician} (today: math) & literature, computation, formal-proof, manuscript, knowledge-mgmt, optimization-backends\\
\mono{librarian} & literature, ingestion, knowledge-mgmt, manuscripts-light\\
\bottomrule
\end{tabularx}
\end{center}

The loader activates a skill iff \mono{requires $\subseteq$ persona.capabilities}. The librarian's
current negative list disappears; tombstone names (entries that resolve only under
\mono{.archive/}) become impossible to carry forward, since a capability gate cannot name a skill the
persona does not declare; and a new persona is one YAML block, not a diff of every registration.

\subsection*{B. Path interpolation and a shared adapter (removes the critical coupling)}

Introduce \mono{\$\{PROFILE\_HOME\}} and \mono{\$\{HERMES\_ROOT\}} tokens in \mono{mcp\_servers}
entries, mirroring the \mono{\{baseDir\}} mechanism skills already use. Concretely:

\begin{enumerate}
    \item Move the generic adapter to a shared location:
    \mono{\textasciitilde/.hermes/tools/mcp\_cli\_adapter.py} (next to \mono{tirith}/\mono{uv},
    which are already cross-profile). Adapter-wrapped tool scripts move with their skills --- they
    do, since \mono{TOOL\_SCRIPT} paths become \mono{\$\{PROFILE\_HOME\}/skills/...}.
    \item Each profile's config then references only its own tree; the librarian stops importing from
    math. Verification is trivial: no path in a profile's config may contain another profile's name.
\end{enumerate}

\subsection*{C. Service registry (removes the endpoint coupling)}

A \mono{services.yaml} naming services abstractly, with endpoints resolved from env at load time:

\begin{lstlisting}[language=Python]
# ~/.hermes/services.yaml
lightrag:   { url: ${LIGHTRAG_URL},  key: ${LIGHTRAG_API_KEY} }
searxng:    { url: ${SEARXNG_URL} }
zimi:       { url: ${ZIMI_URL} }
vikunja:    { url: ${VIKUNJA_URL},   token: ${VIKUNJA_TOKEN} }
siyuan:     { url: ${SIYUAN_URL},    token: ${SIYUAN_TOKEN} }
calibre:    { url: ${CALIBRE_BASE_URL} }
honcho:     { url: ${HONCHO_BASE_URL} }
\end{lstlisting}

MCP entries then reference \mono{\$services.lightrag.url} etc. The .env files remain the secret
store (never committed), but IPs move out of configuration logic into environment, so a service
migration is an env edit, not a per-profile config surgery. This also fixes the calibre asymmetry:
one definition, activated by capability \mono{ingestion}.

\subsection*{D. Toolchain bundle (removes the sandbox coupling)}

The sandbox home is a \emph{capability artifact} (computation, formal proof and manuscript),
not profile state. Split it: keep identity files (\mono{.gitconfig}, \mono{.ssh}, \mono{.bashrc}) in
the profile; extract the toolchain into an installable bundle \mono{math-toolchain.tar} or a Docker/
conda-spec manifest that any persona declaring the relevant capabilities can provision on demand ---
and that a project without formal-proof needs (e.g.\ pure numerical work) never pays for.

\subsection*{E. Project binding files (the actual project-independence mechanism)}

A new math project is then attached by a single file at its root:

\begin{lstlisting}[language=Python]
# ~/Code/<NewProject>/.agent.yaml
profiles: [math, librarian]
working_dir: .
vikunja_project: <id>            # task ledger target
lightRAG_collection: <project>    # literature namespace
sage_env: sage                   # toolchain bundle component (conda env name)
\end{lstlisting}

Profiles discover projects by scanning their \mono{repo\_scan\_roots}; a profile picks up a project's
binding at session start and overrides \mono{terminal.cwd}, ledger targets, and collection names
from it. Nothing inside the profiles is edited when the project changes --- which is exactly the
property today's coupling list (Table~\ref{tab:couplings}) shows to be absent.

\subsection*{F. Remediation prerequisites}

Before any of A--E is built, four live defects should be fixed in place (each a one-line or
one-file change): repoint \mono{hermes-irene} at the merged Irene tree (or disable it for the
librarian), prune the tombstone-only names from the disabled lists, remove \mono{simplerag-memory}
from \mono{math-research-workflow}'s related-skill list, and give math a real calibre server command or
delete its env-only block. These are recorded here as open work items; none is applied by this
documentation project.

\subsection{Why these tools}\label{sec:whytools}

The components above were not assembled from a preference list; they are the ones that satisfied six
constraints at once, and each constraint is a property the workflow depends on.

\begin{itemize}
    \item \textbf{Self-hosted and open source.} The retrieval cascade is deliberately local-first, and a
    tier that bills per query or throttles by contract cannot be its first stop. Every knowledge and
    retrieval component runs on the same host as the profiles.
    \item \textbf{An HTTP API, not only a user interface.} A service becomes a tool only through the
    adapter pattern of Appendix~\ref{app:mcp}, which introspects a command-line tool and publishes it.
    A component whose only interface is a web page cannot be reached by the workflow at all.
    \item \textbf{One container, with its state in a volume.} The whole plane is a single compose
    project. Anything requiring a cluster, an operator or a managed control plane was out of scope
    before its features could be considered.
    \item \textbf{Storage in an open, inspectable format.} Markdown, Postgres, ZIM archives and a
    property graph are all readable without the tool that wrote them. The knowledge base is meant to
    outlive the tooling around it.
    \item \textbf{A footprint that fits a workstation.} The plane runs beside the research machine
    rather than in a data centre; the two components that need real resources --- the inference server
    and the ebook library --- were left outside the stack for that reason
    (Table~\ref{tab:stackexternal}).
    \item \textbf{A role with no cheaper local substitute.} Each component answers a call the six
    stages actually make: a task to open, a document to ingest, an article to ground, a formula to
    find again.
\end{itemize}

covers retrieval and the platform beneath it. In both, the alternatives are live substitutes rather

Two of the choices were not free, and the distinction is worth keeping. Cross-session memory is a

\subsection{Deployment notes}

The stack is a single compose project, and no credential is stored in it: every one is interpolated
from an untracked environment file whose template ships with the project as a list of placeholders.
Bind-mounted service data resolves under one configurable root, so the same file serves both a fresh
install and a migration onto existing data, while the memory service's database and cache use named
volumes. Two images are built from source and their build contexts are supplied; the retrieval
service runs its published upstream image, with the local-build variant given as a commented
alternative.

The stack was validated against the live installation rather than merely parsed. The compose
configuration resolves cleanly, a dry run produces the complete creation plan, and that plan matches
the running containers one for one --- identical container names and identical published host ports
for all sixteen components.

\section{The Model Context Protocol Bridge}\label{app:mcp}

Section~\ref{sec:mcp} described the bridge between the profiles and their tools; this appendix
enumerates what crosses it. Every capability the profiles reach without a shell goes through a Model
Context Protocol server, and every server is registered in the profile's configuration under a name
that becomes the first half of the tool name the model sees. Thirteen servers are registered in each
profile, exposing seventy-five tools in total, and they divide into two families by construction
rather than by purpose.

\subsection{Conventions of the bridge}

Three conventions govern the whole layer, and each of them is visible in the tables below.

\begin{itemize}
    \item \textbf{Naming.} A tool is addressed as \mono{mcp\_\_} followed by the server name and the
    tool name, each pair separated by a double underscore --- for example the task-creation tool of
    the ledger server. The name is derived from the registration, not chosen by the server, so
    renaming a server renames every tool it exposes.
    \item \textbf{Families.} A \emph{native} server speaks the protocol directly: it implements the
    tool list and the call handler itself. A \emph{CLI-adapter} server is a thin wrapper around an
    ordinary command-line tool --- the adapter introspects the tool's argument parser at startup,
    publishes each subcommand as a tool with a JSON schema for its arguments, and rebuilds a command
    line from the call it receives. Nine of the thirteen servers are adapters, and the pattern is why
    adding a new service-backed capability costs a script and a configuration entry rather than
    protocol code.
    \item \textbf{Credentials.} Every server receives its endpoint and secret through environment
    variables declared in the registration, not in the script. The scripts are therefore portable
    between profiles and machines, and the same registration block appears verbatim in both profiles.
\end{itemize}

The servers divide into those that compute, those that verify and those that retrieve --- Tables
\ref{tab:mcpcompute} and \ref{tab:mcpknow} --- and the two tables together account for the whole
registration list of either profile.

\subsection{What each server exposes}

Each server is described below in the order the tables introduce it: what it exposes, and how the
workflow actually spends it.

\begin{description}

\item[\mono{sagemath}] Ten tools over a local SageMath installation: \mono{sage\_solve},
\mono{sage\_diff}, \mono{sage\_integrate}, \mono{sage\_simplify}, \mono{sage\_factor},
\mono{sage\_expand}, \mono{sage\_latex}, \mono{sage\_matrix}, \mono{sage\_number\_field} and
\mono{sage\_run\_script}. This is the first stop of the computation stage, and the one that carries
exactness: a computation that can be done symbolically is done here rather than numerically, and the
\mono{sage\_latex} tool exists so that a verified expression can be moved into a manuscript without
retyping it.

\item[\mono{lean4}] Four tools against a pinned library project: a file checker, a library search, an
ad-hoc evaluation entry point and an automated prover. The verification stage runs on this server
alone, and its discipline is what makes the stage worth having --- a check must name its project
directory explicitly, because a check without a library context compiles against nothing and proves
nothing.

\item[\mono{wolfram-alpha}] Three tools wrapping the public API: a short answer, a validation call
and a verification call. It is used for questions whose answer is a closed form or a number, in
particular when the local stack is unavailable or when an independent implementation is wanted as a
cross-check on a SageMath result.

\item[\mono{scientific-coding}] Four tools running Python inside a sandbox with a CPU-second and
memory ceiling declared in the registration. This is where numerical experiments, plots and
simulations run when they must not touch the host, and one of the tools writes a result into the note
store, which is how an experiment's output reaches the knowledge base without a shell command.

\item[\mono{searxng}] A single search tool over the federated metasearch container. It is the
live-web arm of the retrieval cascade and is deliberately last in preference order: the cascade tries
local sources first and reaches the open web only when they cannot answer.

\item[\mono{zimi}] Four tools over the offline archive container: search, retrieval, reading a
document and suggesting a follow-up. It is the archival-grounding step --- encyclopedic and
historical facts are settled here, in under a second, before a rate-limited web search is spent on
them.

\item[\mono{lightrag-query}] Three tools over the graph-RAG container: a query, a streaming query
and a data query. It answers multi-hop questions across the ingested literature lake and is the only
way the profiles reach the entity graph, which makes the ingestion pipeline a prerequisite for the
literature stage rather than a parallel activity.

\item[\mono{vikunja}] Fifteen tools, the largest surface in the bridge, split between projects
(list, search, get, create, update) and tasks (list, overdue, search, get, create, update, delete,
complete, log). It carries the first and last stages of the workflow: the decomposition stage opens a
task and a hypothesis tree through it, and the close-out stage records the outcome in the same
structure. Its second role is continuity --- the ledger, not the conversation, is what a later
session reads to find out what was decided and what is still open.

\item[\mono{siyuan}] Seven tools over the note store: create, read, update and search documents and
blocks. It is the human-readable layer of the knowledge base, used when a finding should be legible
rather than machine-queryable, and its equation blocks are how a verified formula survives from the
computation stage into a manuscript draft.

\item[\mono{zotero}] Seven tools over the bibliography: searching the library, adding an entry by
identifier, listing collections, exporting BibTeX and synchronising a bibliography file. It sits
immediately after the citation verification gate in the literature stage --- a reference is verified
against primary metadata first and only then added to the library, so the library never accumulates a
citation that has not been checked.

\item[\mono{latex-manuscript}] Five tools over the local TeX installation: compile, an
abstract-syntax-aware edit check, glossary generation, a notation audit and a diff-patch applier.
This is the manuscript stage's whole tool surface, and its two unusual members are the ones that
matter: the edit check catches structural damage that a successful compile would not, and the
notation audit catches the same symbol carrying two meanings across sections.

\item[\mono{calibre}] Twelve tools for library management and format conversion, registered as a
native server in the librarian and as an environment-only block in math --- the same name with
different meanings in the two profiles, noted in Section~\ref{sec:defects}. Its role is ingestion:
converting an acquired book or paper into a form the knowledge base can absorb.

\item[\mono{hermes-irene}] Not a working server. Both profiles register it against a script inside a
development worktree that was merged into the main package and then deleted, so the registration
dangles: dormant in math, enabled and failing at start-up in the librarian. It is listed here because
the bridge's inventory is only complete if its one broken member is in it, and because the correct
replacement --- a bridge to the numerical backend the profiles invoke by shell today --- remains the
open item recorded in Section~\ref{sec:defects}.

\subsection{Notes on the bridge}

\textbf{The bridge is not capability-gated.} Both profiles register the same thirteen servers, and all
of them are enabled in both. What differs between the profiles is which \emph{skills} are active, not
which tools exist: the librarian's skill list disables the computational and proof surface, yet the
librarian's configuration still carries a live handle to it. Capability gating at the skill layer and
capability gating at the bridge layer are two different things, and only the first is implemented
today.

\textbf{Seventy-five tools are exposed.} The count is dominated by the ledger (fifteen) and the
library server (twelve); the two servers that carry the intellectual weight of the workflow, the
computer-algebra system and the proof assistant, expose ten and four. Tool count is therefore a poor
proxy for importance here --- a point the abstraction layer of Section~\ref{sec:abstraction} has to
respect, since a capability gate keyed on the bridge would grant far more than the workflow needs.

\textbf{One capability of the workflow is not on the bridge at all.} Cross-session memory is served
by a built-in provider rather than an MCP server, so it is absent from the inventory above by
construction: the memory service of Appendix~\ref{app:stack} is reached by the runtime, not by a
tool call. The same is true of web search and file access, which are built-in tools rather than
registered servers.

\textbf{Every path in the bridge resolves into the math profile.} The registrations of both profiles
--- including the librarian's, which has no script directory of its own --- point at scripts inside
the math profile's tree. This is the cross-profile coupling of Section~\ref{sec:defects} seen from the
bridge's side: the bridge is the single largest thing that would break if the math profile were moved
or deleted.

\subsection{Notes on the catalog}

\textbf{The two catalogs are the same catalog.} Each profile carries fifty-seven skill entries, and
their union is fifty-nine: only four entries are exclusive to one profile --- the development workflow
for the numerical backend and the exact-gate-scripts skill in math, and the two ingestion skills in
the librarian. Everything else is present in both trees, and the profiles differ only in what is
switched on.

\textbf{Activation is a negative specification.} Math disables twelve names and the librarian
twenty-eight, and the librarian's longer list is precisely the computational and proof surface the
math profile exists to provide. Resolving those names against the live trees gives three outcomes:
five of math's and eighteen of the librarian's disabled names match a skill in the profile tree; six
and nine respectively match only an entry in the curator's archive, meaning they are residue from
skills already retired; and one name in each list --- a local-inference skill that was never installed
--- matches nothing at all. The distinction matters because resolution is by leaf name: a disabled
entry that matches only an archived skill, or nothing, will silently disable a same-named skill the
day one is installed.

\textbf{One gate is inverted.} The community-reading skill is disabled for math and enabled for the
librarian --- the only entry whose activation runs opposite to every other difference between the two
profiles, and the clearest evidence that the disabled lists were assembled by hand rather than
derived from a role.

\textbf{One reference is orphaned.} The designated workflow names a memory skill that exists in
neither catalog, and part of that reference is a shell invocation of a client script that does not
exist either. It is the same class of defect as the dangling server registration in
Appendix~\ref{app:mcp}: a name recorded in one place and never created in another.
